## مشخصات پروژه

* برند: `Ahan Asa | آهن آسا`
* دامنه اصلی: `ahanassa.com`
* زبان زمان راه‌اندازی: فارسی، کاملاً RTL
* زیرساخت اصلی: Cloudflare
* ERP: Odoo در `odoo.ahanassa.com`
* سایت یک پلتفرم B2B برای معرفی خدمات تأمین آهن‌آلات، نمایش اطلاعات محصولات و دریافت درخواست استعلام است.
* سایت در فاز اول فروشگاه اینترنتی، مارکت‌پلیس، تابلوی موجودی لحظه‌ای، پنل مشتری یا سیستم پرداخت آنلاین نیست.
* سرعت بارگذاری، امنیت، قابلیت نگهداری و SEO باید جزو الزامات معماری باشند، نه کارهای بعد از توسعه.

## معماری پایه مورد انتظار

معماری را به‌صورت Cloudflare-native و edge-first طراحی کن و حداقل این اجزا را بررسی و مشخص کن:

* Next.js App Router
* React Server Components به‌صورت پیش‌فرض
* TypeScript در حالت Strict
* Cloudflare Workers برای Runtime
* Cloudflare D1 برای Public Read Model، وضعیت Sync و RFQ Ingress Ledger
* Cloudflare R2 برای رسانه‌ها و فایل‌های خصوصی
* Cloudflare Queues برای پردازش‌های غیرهم‌زمان
* Cloudflare Turnstile برای مقابله با سوءاستفاده
* Cloudflare WAF و Rate Limiting
* Cron Triggers یا Scheduled Workers برای Syncهای زمان‌بندی‌شده
* Cache در Edge
* محیط‌های مجزای Development، Preview، Staging و Production

در صورت ناسازگاری نسخه فعلی Next.js یا یکی از قابلیت‌ها با Cloudflare Workers، محدودیت را شفاف ثبت و راه‌حل سازگار پیشنهاد کن. هیچ وابستگی به Node.js Runtime را بدون بررسی سازگاری Cloudflare وارد نکن.

## مرزبندی Odoo و وب‌سایت

Odoo را منبع اصلی داده‌های تجاری در نظر بگیر، از جمله:

* محصولات
* گونه‌ها و مشخصات محصولات
* واحدهای اندازه‌گیری
* فهرست‌های قیمت
* مشتریان و مخاطبان
* CRM Leads
* درخواست‌های استعلام
* پیش‌فاکتورها و Quotations
* فروش
* خرید
* موجودی
* حسابداری

وب‌سایت یا CMS سایت مسئول این موارد باشد:

* مقالات
* محتوای صفحات
* داده‌های SEO
* Metadata
* محتوای چندزبانه
* Public Product Projection
* نسخه Cache‌شده قیمت‌های قابل نمایش
* تاریخچه Snapshotهای قیمت در صورت تأیید
* RFQ Ingress Ledger
* وضعیت Sync و خطاهای Integration

قیمت‌ها فقط در Odoo ویرایش شوند. اپراتور نباید دو منبع مستقل برای تغییر قیمت داشته باشد.

وب‌سایت عمومی نباید برای Render شدن صفحات، به‌صورت هم‌زمان و مستقیم Odoo را فراخوانی کند. اطلاعات عمومی موردنیاز باید به‌شکل غیرهم‌زمان از Odoo دریافت، اعتبارسنجی و در D1 ذخیره شود.

قطع بودن Odoo نباید باعث از دسترس خارج‌شدن صفحات عمومی سایت شود. آخرین داده معتبر Cache‌شده باید باقی بماند و Sync ناموفق نباید داده سالم قبلی را بازنویسی کند.

ارتباط با Odoo باید فقط از طریق یک Server-only Adapter انجام شود. اطلاعات ورود، API Key، Session، Database Name و سایر Secrets نباید به مرورگر، HTML، Client Bundle، Log عمومی یا Analytics منتقل شوند.

معماری مدیریت محتوا را به شکلی تعریف کن که اپراتور مجاز بتواند:

کامپوننت‌های صفحه نباید مستقیماً به SDK مربوط به CMS وابسته باشند. دسترسی باید پشت Repository Interface یا Adapter قرار بگیرد.

## فرم استعلام و ارسال لیست آهن‌آلات

بازدیدکننده باید بتواند یک RFQ شامل چند ردیف ثبت کند. هر ردیف باید حداقل از این فیلدها پشتیبانی کند:

* دسته‌بندی
* محصول یا Variant
* سایز یا مشخصات
* واحد
* مقدار اعشاری
* توضیحات
* عنوان، سایز و واحد سفارشی برای اقلامی که در کاتالوگ نیستند

اطلاعات مشتری نیز باید بتواند شامل نام، شرکت، شماره تماس، ایمیل، شهر، توضیحات و روش تماس ترجیحی باشد.

کاربر باید بتواند فایل‌های موردنیاز مانند Excel، PDF و تصاویر مجاز را بارگذاری کند.

معماری RFQ باید این ویژگی‌ها را داشته باشد:

1. اعتبارسنجی Client-side فقط برای تجربه کاربری باشد.
2. اعتبارسنجی Server-side مرجع نهایی باشد.
3. دسته‌بندی، محصول، واحد و مقادیر ارسالی با داده معتبر سمت سرور تطبیق داده شوند.
4. درخواست و تمام ردیف‌های آن قبل از نمایش پیام موفقیت، به‌صورت Durable ذخیره شوند.
5. برای هر درخواست یک Reference Number تولید شود.
6. یک Idempotency Key از ثبت تکراری جلوگیری کند.
7. انتقال RFQ به Odoo به‌صورت Async انجام شود.
8. Sync با Odoo قابلیت Retry، Dead-letter handling و مشاهده وضعیت داشته باشد.
9. ثبت تکراری Lead یا Opportunity در Odoo کنترل شود.
10. اختلال Odoo باعث گم‌شدن درخواست مشتری نشود.
11. فایل‌ها مستقیماً به فضای خصوصی R2 و با مجوز کوتاه‌مدت بارگذاری شوند.
12. فایل خصوصی Public URL دائمی نداشته باشد.
13. محدودیت نوع، حجم، تعداد فایل و سیاست نگهداری مشخص شود.
14. در صورت نیاز، مسیر Quarantine و Malware Scanning به‌عنوان Decision Gate تعریف شود.

## قواعد Claude Code

در انتهای سند، قواعد الزام‌آور زیر را درج کن:

* قبل از پیاده‌سازی، `CLAUDE.md`، `DO_NOT_CHANGE.md` و اسناد مرجع مرتبط خوانده شوند.
* هیچ Secret یا Credential در کد، Client Bundle یا مستندات ثبت نشود.
* مرورگر هرگز مستقیماً با Odoo ارتباط نگیرد.
* صفحات عمومی برای Render شدن به پاسخ زنده Odoo وابسته نباشند.
* قیمت فقط در Odoo ویرایش شود.
* RFQ پیش از پیام موفقیت باید Durable ذخیره شده باشد.

* Client Component فقط در صورت نیاز واقعی ساخته شود.
* از `any`، اعتبارسنجی ناقص و Swallow کردن خطاها جلوگیری شود.
* هر قابلیت جدید باید تست، Loading State، Error State و رفتار Accessible داشته باشد.
* تصمیم حل‌نشده نباید با حدس پیاده‌سازی شود.
* تعارض اسناد باید در `DECISIONS.md` یا ADR ثبت شود.
* تغییر معماری بدون ثبت دلیل و اثرات آن ممنوع باشد.

* فایل را با نام دقیق `TECHNICAL_ARCHITECTURE.md` در ریشه پروژه ذخیره کن.
* متن سند باید به زبان انگلیسی فنی، روشن و اجرایی نوشته شود.
* نام‌های فارسی برند و Routeهای فارسی را بدون تغییر نگه دار.

* برای هر تصمیم مهم، دلیل، پیامد و محدودیت اجرایی را مشخص کن.
* موارد تأییدنشده را با برچسب `Decision Gate` یا `TBD` ثبت کن.
* هیچ قابلیت یا Integration جعلی ایجاد نکن.
* اگر فایل از قبل وجود دارد، ابتدا آن را کامل بخوان و سپس بدون حذف تصمیم‌های معتبر، با این معماری یکپارچه و به‌روز کن.
* از تکرار مطالب و توصیه‌های مبهم اجتناب کن.
* خروجی نهایی فقط محتوای کامل فایل `TECHNICAL_ARCHITECTURE.md` باشد و توضیح اضافی خارج از فایل ارائه نشود.
