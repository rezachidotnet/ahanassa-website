### DAR-030 — RFQ abuse protection implemented: mandatory server-side Turnstile Siteverify + Workers Rate Limiting binding, closing the "real Turnstile/rate-limiting" gap left open by DAR-023/DAR-024 (new, 2026-08-29)

**Severity:** P2 — informational; closes a previously-documented gap, no schema/architecture change
**Status:** RESOLVED FOR THIS PASS (code + tests); production widget/secret provisioning remains a deployment gate, not closed by this entry
**Finding:** DAR-023/DAR-024/DAR-028 each explicitly listed "real Turnstile/rate-limiting" as a still-open item — until this pass, `POST /api/rfqs` had only the passive honeypot/timing signals (`components/contact/enquiry-form.tsx`, `lib/rfq/service.ts`). This entry adds two additional, layered checks ahead of D1 persistence, without removing the existing ones.

**What was implemented:**

- `lib/security/turnstile.ts` (`verifyTurnstileToken`) — mandatory server-side Siteverify (`POST https://challenges.cloudflare.com/turnstile/v0/siteverify`), 5s bounded timeout via `AbortController` (same pattern as `lib/odoo/client.ts`), validates the `rfq_submit` action (`lib/security/turnstile-action.ts`, shared with the client widget), and fails closed on every non-`success:true` outcome. Distinguishes a visitor-side failure (`reason: "invalid"` → `403 VERIFICATION_FAILED`) from an operational failure (`reason: "unavailable"` — missing secret, network error, timeout, non-2xx, malformed JSON → `503 SERVICE_UNAVAILABLE`), per the task's explicit "Fail Closed" instruction. Wired into `lib/rfq/service.ts#submitRfq`, after the existing honeypot/timing checks and strictly before the idempotency lookup/D1 write — no code path reaches `createRfq` without a verified token.
- `lib/security/rate-limit.ts` / `lib/security/rate-limit-binding.ts` — Cloudflare Workers Rate Limiting binding (`RFQ_RATE_LIMITER`, `wrangler.jsonc` `ratelimits`, `namespace_id` `1001` top-level / `1002` staging, `simple: { limit: 5, period: 60 }` — the only Cloudflare-supported period values are 10 or 60). Split into a pure core (no `cloudflare:workers` import, unit-testable with a fake binding) and a thin binding wrapper (mirrors the split already used between `lib/odoo/client.ts` protocol mechanics and env-sourced config), because a static `cloudflare:workers` import breaks the project's plain `node --test` runner even when unused by the imported test. Keyed by a SHA-256 hash (Web Crypto, same primitive as `lib/rfq/idempotency.ts`) of the Cloudflare-injected `cf-connecting-ip` header — never a client-supplied `X-Forwarded-For`, never the raw IP itself, never persisted to D1. Fails **open** when the binding itself is absent (documented deviation: unlike Turnstile's fail-closed behavior, the binding is an abuse-*reduction* layer per Cloudflare's own "permissive, eventually-consistent, per-location, not an exact ledger" documented semantics — the mandatory Turnstile check remains the actual fail-closed gate regardless of rate-limiter binding availability). Wired into `app/api/rfqs/route.ts`, immediately after the existing cheap same-origin/content-type/content-length checks and before the request body is ever read — a rate-limited request never reaches JSON parsing, schema validation, or Turnstile Siteverify.
- Final request order (`app/api/rfqs/route.ts` header comment): same-origin → content-type → content-length → rate limit (`429`) → body read/size → JSON parse → [`submitRfq`: schema validation (`422`) → honeypot/timing (`422`) → Turnstile Siteverify (`403`/`503`) → idempotency hash + atomic D1 batch write (`201`) → best-effort outbox publish]. The existing idempotency mechanism (`rfqs.idempotency_key_hash` unique lookup in `lib/rfq/repository.ts#createRfq`) is unchanged and untouched by this pass — a client retry with the same `idempotencyKey` still returns the original reference rather than creating a duplicate, regardless of whether it presents a fresh Turnstile token (single-use tokens are consumed once per Siteverify call; a UI-level retry always fetches a new token via `turnstile.reset()`, but the *server's* duplicate-prevention guarantee does not depend on that — it is keyed on `idempotencyKey`, which the client keeps stable across retries of the same logical submission).
- `components/contact/enquiry-form.tsx` — Turnstile managed widget, explicit render (`window.turnstile.render`, via `next/script` for the `api.js` loader), `action: "rfq_submit"`, `language` explicitly mapped from the existing `fa`/`en`/`ar` locale prop (not left to Turnstile's own auto-detection, since the site already threads an authoritative locale through every page). ### DAR-036 — Website-owned catalog editorial/publication workflow designed between DB_PUBLIC's real 237-variant commercial data and future public catalog UI; no migration needed, hard public-read safety boundary added, full lifecycle proven end-to-end against real staging data (new, 2026-08-30)

**Trigger:** with real, synced commercial catalog data now in both DB_PUBLIC databases (DAR-035) but zero editorial/SEO content and zero publication, a task requested designing and implementing the Website-owned editorial layer that sits between Odoo's commercial truth and any future public catalog page — an explicit state machine, a single reusable publication-eligibility predicate, per-locale independence, slug architecture, and safe bootstrap of the 237 existing products — without building any admin UI, authentication system, or public write endpoint, and without auto-publishing anything.

**Schema audit — no migration required.** `product_seo_contents` (`migrations_public/0001_catalog_schema.sql`, already applied to both databases) already provides every editorial field requested: `h1` (title), `slug` (unique per `(slug, locale)`), `intro` (short description), `body_json` (long description), `seo_title`/`seo_description`, `index_status` (indexability), `content_quality_status` (review state), and `published_at` (publish state, nullable). Combined with the pre-existing, never-synced `product_variants.is_public` master switch, this fully satisfies the task without any additive migration — the safest possible answer given the task's own "no destructive migrations, all 237 rows must survive" constraint and the standing guardrail against repeating migration 0002's DROP+recreate pattern. `needs_editorial_setup` is deliberately **not** a stored column — it is derived as "no `product_seo_contents` row exists for `(entity, locale)`," avoiding a flag that could drift out of sync with the row's actual existence.

**Editorial state machine — two independent axes, not a new enum:** `content_quality_status` (`incomplete → review → approved`, and back) crossed with `published_at` (null/timestamp) together express six conceptual lifecycle states (`needs_setup`/`draft`/`review`/`ready`/`published`/`unpublished`) — `lib/catalog/editorial.ts#describeLifecycleState`. Content-status transitions are validated (`incomplete↔review↔approved`, no direct `incomplete↔approved` jump) via `isValidContentStatusTransition`, exhaustively unit-tested. **Policy decision, recorded in code comments and this DAR entry:** editing published content (`upsertEditorialDraft`) never auto-changes `content_quality_status` or `published_at` — only an explicit, separate call (`reopenForEdits`/`unpublishContent`) takes content offline. Archiving a variant in Odoo (`is_active = 0`) makes it correctly invisible immediately via the eligibility predicate but never touches `is_public`/`product_seo_contents`; reactivating it (`is_active = 1`) never auto-restores Website publication, because sync has no write path to either field — proven structurally, not just by convention: a new test (`sync.test.ts`, "commercial patch never includes isPublic") asserts `VariantCommercialPatch`'s key set never contains `isPublic`, even when a reactivation (`isActive: false → true`) is present in the same patch.

**Single canonical publication-eligibility predicate** (`lib/catalog/editorial.ts#evaluatePublicationEligibility`) replaces any risk of scattered `is_public && active && title != null` checks: `visible = isActive && isPublic && seoContent exists && content_quality_status === 'approved' && published_at !== null && h1/slug non-empty`; `indexable = visible && index_status === 'index'` — `indexable` can never be `true` when `visible` is `false` (asserted directly in tests). `lib/catalog/editorial-repository.ts#getPublishedCatalogProducts`/`getPublishedCatalogProductBySlug` implement the identical rule as the only SQL path into `product_variants`/`product_seo_contents` for public consumption — a structural "hard safety boundary," not a filter that can be bypassed by a different caller.

**A real, pre-existing safety gap found and fixed (zero blast radius):** `lib/catalog/repository.ts`'s original "public" read functions from Tasks 4/5 (`getPublicVariantByXid`, `getPublicVariantsByGroup`, `getPublicVariantBySlug`, `getApprovedSeoContent`, `getVariantsNeedingEditorialSetup`, `getProductByTemplateXid`) filtered only on `product_variants.is_active`/`is_public`, never on whether real, approved, published editorial content actually existed for a locale — they would have returned a variant as "public" the moment `is_public` flipped true, even with zero SEO content. Verified via grep that nothing outside `repository.ts` called any of them (only `lib/catalog/sync-runner.ts` uses this file, and only for its 5 sync-facing exports), so removal was a safe, zero-blast-radius fix rather than a breaking change. They were removed entirely and replaced by the properly-gated equivalents in the new `lib/catalog/editorial-repository.ts`. `repository.ts` is now scoped exclusively to the commercial sync path (263 lines, 5 functions + 2 helpers) and its file header now states this boundary explicitly.

**Per-locale independence, live-proven:** FA, EN, AR publication states are fully independent per `(entity, locale)` row — a temporary live test on staging published a FA row while zero EN rows existed at all for the same variant, and confirmed the EN-locale eligibility query correctly still returned zero results. `product_variants.name_fa`/`slug_fa` (the Odoo-bootstrapped operational fallback label, DAR-034/035) is never read by the eligibility predicate or either public repository query — only a real, human-progressed `product_seo_contents` row can make a product publicly visible, in any locale, structurally preventing a fallback label from ever being mistaken for completed editorial work.

**Slug architecture:** public slug identity lives entirely in `product_seo_contents.slug` (never `product_variants.slug_fa`), uniqueness enforced at the DB level per `(slug, locale)` — live-proven by deliberately attempting a conflicting slug `INSERT` on staging and receiving a real `UNIQUE constraint failed: product_seo_contents.slug, product_seo_contents.locale` error. `lib/catalog/editorial.ts#normalizeSlug`/`isValidSlug` provide deterministic ASCII normalization; Persian/Arabic input normalizes to an invalid result by design (callers must supply an already-transliterated candidate — the same "no fabricated translation" discipline extends to slugs). No `product_variant_xid` ever appears in a slug. No redirect-history table was built (not yet needed), but the design does not block adding one later.

**SEO/indexability boundary — four distinct concepts, not one boolean:** commercially selectable (`is_active` alone — independent of publication, since a variant may need to remain RFQ-selectable without any indexable SEO page — an explicit requirement of this task), publicly browsable (`visible`), SEO indexable (`indexable`, strictly a subset of `visible`), and featured/family landing page (not built — `product_seo_contents.entity_type` already supports `'product'` as a template-level row, an existing, unused extension point).

**Variant-vs-template SEO page granularity — explicitly left open, per this task's own instruction not to decide route architecture without an authoritative routing/design doc.** 237 variants / 13 templates; the schema supports either a per-variant page, a per-template landing page, or a hybrid, without any further migration — recorded as an open question in the new canonical doc, not resolved here.

**Live end-to-end proof against real staging D1 (no Worker deployed, no HTTP endpoint created — SQL run directly via `wrangler d1 execute --remote`, mirroring the exact `editorial-repository.ts` queries):** confirmed baseline (237 variants needing FA setup, 0 published); created one temporary `product_seo_contents` row on a real variant, flipped its `is_public` to `1`, walked it `incomplete → review → approved` (confirmed still 0 publicly eligible while `published_at` was `NULL`), then set `published_at` (confirmed exactly 1 row now returned by the public-read query, with correct joined data, and confirmed the EN locale independently still returned 0); proved the slug-uniqueness constraint as above; then fully deleted the test row and reverted `is_public`, re-verifying staging was restored to the exact original baseline. **Production was checked read-only** (confirmed identical, unchanged baseline) — the mutating lifecycle test was deliberately not repeated there, following DAR-035's precedent of not redundantly risking production once staging has proven the identical logic against the identical schema.

**Current editorial state, both databases (2026-08-30, unchanged from DAR-035's baseline — nothing was published or altered by this task):**

|---|---:|---:|
